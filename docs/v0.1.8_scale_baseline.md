# ManifoldGuard v0.1.8 Candidate-Pool Scale Baseline

Status: measured development baseline

Measurement date: 2026-07-11

This document records development performance evidence, not a public accuracy
or generalization claim.

## Workload

- Source: `data/csv_exports/mbt5_exp20_master_candidate_ledger.csv`
- Candidate rows: `257`
- Cases represented: `53`
- References: unique valid-labelled candidate text from the same frozen ledger
- Mode: offline (`use_embeddings=False`)
- Warmup iterations: `3`
- Measured iterations: `10`

The valid-labelled rows are used as one synthetic reference manifold only to
exercise the current implementation at the frozen ledger's scale. The emitted
action and safe/blocked split are not accuracy evidence for this mixed-case
pool.

## Environment

```text
Python: CPython 3.13.13
Platform: Windows 10.0.19045
```

These timings are machine-specific and should be compared with later runs on
the same machine and power profile.

## Interpretation and next target

- Keep normalized duplicate grouping; it avoids `69` evaluations on the
  canonical 257-row workload.
- Do not optimize Markdown, CSV, or JSON construction first.
- Do not add memory complexity based on this traced-allocation baseline.
- Profile-guided inspection found repeated single-clause negation parsing as
  the first behavior-preserving candidate-side cleanup.
- Continue profiling the remaining relation-helper hotspots before attempting
  broader caching or concurrency changes.
- Require behavior parity and the frozen regression suite before accepting any
  runtime optimization.

## Profile-guided negation-parser follow-up

`cProfile` identified candidate relation and negation extraction as the dominant
regulation work. The first bounded cleanup removes a duplicate call to the same
segment extractor when normalized negation text contains only one relation
segment. Coordinated clauses retain the whole-text pass needed for cross-segment
binding.

An alternating 30-round microbenchmark over all `188` unique normalized texts
in the frozen workload measured:

| Negation parser | Median per workload pass |
|---|---:|
| Before duplicate-pass removal | 62.623 ms |
| After duplicate-pass removal | 54.084 ms |

That is a `13.636%` parser-level reduction and `8.539 ms` median saving per
188-text pass. Every extracted negation set and every end-to-end candidate
decision matched in the comparison. Whole-pool timing was too variable during
the paired run to support a reliable end-to-end percentage claim, so this is
recorded only as a parser-level result.

Local profiling and comparison artifacts are stored under
`D:\Temp\ManifoldGuard` and are intentionally not committed.

## Profile-guided positive-relation follow-up

The next bounded cleanup applies the same single-segment rule to positive
relation extraction. Common temporal, ordinal, permission, token-reuse,
aggregate, range, scope, alias, role, and shared-subject helpers were previously
run against both the whole normalized text and its identical single segment.
Single-clause text now runs those helpers once through the segment extractor;
multi-segment text retains all whole-text context passes. Whole-text identity,
comparative, exception, and permissive conditional handling also remain in
place.

An alternating 30-round microbenchmark over the same `188` unique normalized
texts measured:

| Positive-relation parser | Median per workload pass |
|---|---:|
| Before duplicate common-helper passes | 184.173 ms |
| After duplicate common-helper passes | 134.400 ms |

That is a `27.025%` parser-level reduction and `49.773 ms` median saving per
188-text pass. Extracted relation sets matched for every unique text. A separate
full-workload comparison also matched all `257` candidate records, including
emit/block decisions, scores, clamps, duplicate diagnostics, rankings, and the
emitted text. As with the negation cleanup, no whole-pool speedup percentage is
claimed from these parser-level measurements.

## Empty-negation reuse follow-up

The post-parser profile found `435` negation-extraction calls for `263`
reference-plus-unique-candidate texts. Candidate negations were already
precomputed in `evaluate_candidate`, but `_has_unsupported_negation` used a
truthiness fallback that treated an empty set as absent and reparsed `172`
non-negated candidates. The fallback now distinguishes `None` from an empty
precomputed set.

Across 16 alternating full-pool pairs, every candidate record matched and the
median regulation time measured:

| Empty-negation handling | Median per 257-row pool |
|---|---:|
| Reparse empty precomputed sets | 238.674 ms |
| Reuse empty precomputed sets | 208.244 ms |

This paired run saved `30.430 ms` per pool, or `12.750%`. Unlike the isolated
parser measurements above, this is an end-to-end regulation result for the
frozen synthetic workload on the recorded development machine; it remains a
development performance measurement rather than a cross-machine guarantee.
