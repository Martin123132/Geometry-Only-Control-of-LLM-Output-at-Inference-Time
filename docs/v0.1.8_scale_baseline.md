# ManifoldGuard v0.1.8 Candidate-Pool Scale Baseline

Status: measured development baseline

Measurement date: 2026-07-11

This document records development performance evidence, not a public accuracy
or generalization claim.

## Workload

- Source: `data/csv_exports/mbt5_exp20_master_candidate_ledger.csv`
- Candidate rows: `257`
- Cases represented: `53`
- References: unique valid-labelled candidate text from the same frozen ledger
- Mode: offline (`use_embeddings=False`)
- Warmup iterations: `3`
- Measured iterations: `10`

The valid-labelled rows are used as one synthetic reference manifold only to
exercise the current implementation at the frozen ledger's scale. The emitted
action and safe/blocked split are not accuracy evidence for this mixed-case
pool.

## Environment

```text
Python: CPython 3.13.13
Platform: Windows 10.0.19045
```

These timings are machine-specific and should be compared with later runs on
the same machine and power profile.

## Candidate-pool shape

```text
Submitted candidates: 257
Unique normalized pool groups: 188
Duplicate candidates: 69
Evaluations avoided by grouping: 69
Duplicate compression: 26.8482%
```

The frozen ledger's natural duplicate rows therefore remove more than one
quarter of repeated candidate evaluations without removing audit rows.

## Timing baseline

| Stage | Median | Mean | Min | Max / p95 |
|---|---:|---:|---:|---:|
| Regulation | 758.628 ms | 750.323 ms | 712.918 ms | 787.652 ms |
| Report construction | 1.395 ms | 1.468 ms | 1.066 ms | 2.052 ms |
| Compact JSON serialization | 4.644 ms | 4.952 ms | 3.657 ms | 8.208 ms |
| End to end | 765.913 ms | 756.747 ms | 718.852 ms | 792.761 ms |

Median regulation throughput:

```text
Submitted candidates per second: 338.769
Unique pool groups per second: 247.816
Per submitted candidate: 2.951860 ms
Per unique pool group: 4.035255 ms
```

Regulation accounts for roughly 99% of median end-to-end time. Report
construction and JSON serialization together add about 6 ms, so report
formatting is not the first optimization target.

## Memory baseline

```text
Peak traced Python allocations: 553586 bytes (0.528 MiB)
```

This is a `tracemalloc` measurement of Python allocations, not whole-process
resident memory or native allocator usage. It is low enough that runtime should
be investigated before memory reduction.

## Serialized report sizes

| View | Size |
|---|---:|
| Full compact JSON | 172437 bytes |
| Full Markdown | 142293 bytes |
| Full CSV | 118565 bytes |
| Blocked-only compact JSON | 110147 bytes |
| Duplicate-only compact JSON | 47848 bytes |

The `0.1.7` report filters already provide a substantial payload reduction for
focused audits. Pagination or streaming should wait for a workload where
report size, rather than regulation time, is measured as the limiting factor.

## Interpretation and next target

- Keep normalized duplicate grouping; it avoids `69` evaluations on the
  canonical 257-row workload.
- Do not optimize Markdown, CSV, or JSON construction first.
- Do not add memory complexity based on this traced-allocation baseline.
- Profile reference-side preprocessing and per-unique-candidate regulation next.
- Require behavior parity and the frozen regression suite before accepting any
  runtime optimization.
